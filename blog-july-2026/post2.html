Everybody designs the agent loop. Almost nobody designs what stops it.

That asymmetry is the reason so many agents behave like a car with excellent steering and no brake pedal. It goes where you point it. It goes there very fast. And when the road runs out, it keeps going, confidently, for eleven more iterations.

These are field notes on the stopping half.

The term, and how much weight it holds

Simon Willison named the skill in Designing agentic loops on September 30, 2025, calling it "a critical new skill to develop," with a definition that has aged well because it refuses to be impressive:

An agent is something that runs tools in a loop to achieve a goal.

The loop itself is older. ReAct (Yao et al., 2023) gave us reason → act → observe → repeat, and that cycle is still what's underneath essentially every agent framework shipping today. What changed through 2026 is that people started treating the loop as the design surface rather than an implementation detail — something you specify deliberately, the way you'd specify a schema.

The compressed name for that — "loop engineering" — spread through 2026 via Divy Yadav's Loop Engineering Explained on Medium (June 2026), MindStudio's explainers, and Oracle's The Agent Loop Decoded.

Now the caveat, up front, because it matters. This term is not settled canon. Harness engineering has named originators, essays from OpenAI and Anthropic, and academic uptake. Loop engineering is younger and looser, and a meaningful chunk of its usage is vendor marketing. I'd anchor to Willison and the ReAct lineage, not to whoever is selling you a framework this quarter. The underlying practice is real regardless of what it settles on being called.

The cleanest positioning I've found is in the Buildrix paper (arXiv 2606.25139), which lays out the progression explicitly — prompt engineering → context engineering → harness engineering → loop engineering — and separates the last two like this: harness engineering "connects the model to an executable environment," while loop engineering "extends these ideas by defining how the system repeatedly observes, acts, verifies, and recovers."

So: harness is the surface area. Loop is how that surface iterates over time.

Loops don't crash. They drift.

This is the failure mode worth internalizing, because it defeats every instinct you brought from normal software.

A broken loop rarely throws. It runs. It produces plausible output. It calls the wrong tool, gets a confusing observation back, reasons about the confusing observation, calls the wrong tool again with slightly different arguments, and retries into the same wall while burning tokens with a completely straight face.

There is no stack trace for an agent that confidently did the wrong thing eleven times.

Your exception handler never fires. Your uptime dashboard is green. The only artifacts are a token bill that's up 40% and a user who quietly stopped using the feature.

Success is silent. Failures are verbose.

The strongest self-correction pattern I've seen in circulation comes from HumanLayer, by way of Addy Osmani's write-ups. One sentence:

Success is silent, failures are verbose.

Concretely: run a verification step after each loop iteration, and inject only the failures back into context.

A passing typecheck adds nothing to the model's context — so don't spend the tokens telling it everything went fine. A failing one adds exactly the error text the model needs to fix the thing it just broke. The loop tightens on its own, and context stays clean, because you never paid for the good news.

def step(state):
    output = agent.run(state)
    problems = verify(output)          # typecheck, tests, schema, policy

    if not problems:
        return output                  # silence

    state.append(observation(problems))  # only the errors go back in
    return None                          # loop continues

Osmani's writing also covers the "Ralph Loop" — re-injecting the original prompt into a fresh context window when the agent exits — as a named long-horizon pattern. Same underlying instinct: the loop's memory is a resource you manage, not a log you accumulate.

Worth saying that this generalizes well past code. Anything verifiable can carry a gate. A JSON schema. A SQL dry-run. A retrieval-grounding check. A policy scan. If you can write a function that returns "problems," you can run this pattern.

The two loops, and which failures belong in which

Here's where most teams make the choice that costs them later. They pick one loop.

There are two, they have genuinely different cost profiles, and you need both.

Inner loopOuter loop
TimingSynchronous, inside the execution cycleAsynchronous, beside the pipeline
BehaviorBlocks, raises, retriesScores, alerts, accumulates
CostLatency on every single callNothing on the request path
Right forFailures you must not shipFailures you need to see
Wrong forAnything you'd tolerate for a weekAnything that leaks or costs money now

The mistake in both directions is symmetrical. Put everything in the inner loop and you've added a synchronous LLM judge to your p99 to catch a tone problem. Put everything in the outer loop and you find out about the credential in the response after it reached the customer.

So the design question isn't "block or observe." It's which failures belong in which loop — and that's a question about consequences, not about capability.

In Fluiq this is one flag, deliberately, so the decision stays legible in the code that makes it:

import fluiq

fluiq.instrument(api_key="flq_...")

# inner loop — back-pressure. Raises FluiqEvalError on the request path.
fluiq.eval(mode="block", thresholds={"hallucination": 0.8})

# outer loop — observation. Scored server-side, request path never waits.
fluiq.eval(mode="warn", metrics=["relevance", "coherence"])

In block mode the SDK calls synchronously and raises FluiqEvalError (or FluiqSecurityError) — your loop feels the failure and can react to it, retry against it, or fail the request. In warn mode everything runs server-side over Kafka; scores land in the dashboard and nothing on the request path waits for them.

Same evaluation, two different loops, one keyword.

Why this is a security argument, not just a reliability one

Here's the case that convinced me loop-level thinking is structural rather than stylistic.

Crescendo (Russinovich, Salem & Eldan, arXiv 2404.01833, April 2024; presented at USENIX Security 2025) is a multi-turn jailbreak that escalates gradually across turns that each look benign in isolation. The reported numbers are not marginal — a 98% success rate against GPT-4 and 100% against Gemini-Pro, and on the AdvBench subset the automated variant outperformed prior state-of-the-art jailbreaking techniques by 29–61% on GPT-4 and 49–71% on Gemini-Pro.

Now the part that matters architecturally. Every individual turn passes a per-turn classifier. That's the entire design of the attack. There is no single malicious message to catch, because the attack doesn't live in any message. It lives in the shape of the sequence.

To detect it you need session state across turns — which is a loop-level capability, not a proxy-level one. A gateway that sees one request at a time structurally cannot compute a trend, because it has no sequence to compute over.

Fluiq's detector is a linear-regression slope over the session's per-turn risk scores. Escalation fires at slope ≥ 0.3, with at least three turns and a current risk score above a floor, so a single spiky message doesn't trip it and a slow climb does. The same slope computation, keyed on the agent DAG instead of session time, catches trust-boundary escalation between agents.

You can disagree with those thresholds. What you can't do is compute them one request at a time.

The checklist I'd actually use

Strip away the terminology and loop engineering is five questions you should be able to answer about any agent you run in production:

1. What stops it? Not "what's the max iterations constant" — what is the goal condition, and how does the loop know it's been met? Iteration caps are a timeout, not a termination condition. If your only stop is a cap, your agent doesn't finish, it expires.

2. Do your tools return real observations? A tool that returns {"status": "ok"} has told the model nothing it can reason about. The observe step in reason-act-observe is load-bearing, and a tool that returns nothing useful quietly turns your loop into open-loop generation.

3. What goes back into context, and what doesn't? Success silent, failures verbose. Every token you spend narrating success is a token unavailable for the actual problem.

4. Which failures block and which are observed? Decide explicitly, write it down, and put the two modes next to each other in the source so the next person can see the decision was made on purpose.

5. What do you measure across the whole session, not per call? Escalation, drift, repeated-tool thrash, cost per completed goal. These are trajectory properties. Per-call monitoring is definitionally blind to all of them.

The prompt gets the model to think. The harness gives it something to act on. The loop decides how many times, how it recovers, and — the part everyone underinvests in — when it stops.

Design the loop, not just the prompt.
