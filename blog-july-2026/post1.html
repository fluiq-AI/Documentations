Sometime in the last year, the interesting question about agent quality stopped being "which model?"

I noticed it first in how people described their own wins. A team would tell me their agent got dramatically better, and when I asked what changed, the answer was almost never a model swap. It was a retry policy. A tool description rewritten for the fourth time. A sandbox that stopped truncating stderr. Small, unglamorous plumbing.

There is now a name for that plumbing, and a small body of literature behind it.

Agent = Model + Harness

Vivek Trivedy at LangChain popularized and formalized the term in The Anatomy of an Agent Harness (March 10, 2026). The line people quote back at each other:

If you're not the model, you're the harness.

His definition is deliberately total. The harness is every piece of code, configuration, and execution logic that isn't the model itself. System prompts. Tool definitions and MCP servers. Sandboxes. Orchestration. Hooks and middleware. Observability.

And the consequence, also verbatim: "A raw model is not an agent. But it becomes one when a harness gives it things like state, tool execution, feedback loops, and enforceable constraints."

Trivedy had been circling this for a while. His earlier essay on the Claude Code SDK — subtitled the Birth of HaaS (Harness as a Service), published around September 2025 — argued the industry was moving "from LLM APIs to Harness APIs." At the time that read as a prediction. It reads differently now.

One attribution note, since I'd rather flag it than get corrected in the comments: a minority of write-ups credit Mitchell Hashimoto with the earliest written use of the term, around February 2026. Trivedy provided the formal taxonomy that everyone else builds on. "Popularized and formalized" is the phrasing I'd defend.

The evidence that made people take it seriously

Terms spread on vibes. Disciplines spread on results.

In Improving Deep Agents with Harness Engineering (February 17, 2026), Trivedy's team moved a coding agent from Top 30 to Top 5 on Terminal Bench 2.0 by changing only the harness. The model was held fixed at gpt-5.2-codex. Same weights, same context limits, same everything a model card would tell you about. Five times the rank.

Addy Osmani compressed the finding into the sentence that's been doing the rounds since April 2026:

A decent model with a great harness beats a great model with a bad harness.

That is an uncomfortable claim if your roadmap is a list of model upgrades. It's a liberating one if your roadmap is a list of things you actually control.

Two frontier labs, six weeks apart

What convinced me this wasn't a LangChain-flavored coinage was watching OpenAI and Anthropic arrive at the same place independently, in public, within about six weeks.

OpenAI, February 11, 2026. Ryan Lopopolo published Harness engineering: leveraging Codex in an agent-first world. His framing is that the engineer's job shifts away from writing code and toward "design environments, specify intent, and build feedback loops that allow Codex agents to do reliable work." His team's motto is "Humans steer. Agents execute." The essay describes an internal product built over roughly five months with zero lines of manually-written code — on the order of a million lines and 1,500 pull requests. Michael Bolin's Unrolling the Codex agent loop (around January 2026) is the companion piece on the mechanics.

Anthropic, March 24, 2026. Prithvi Rajasekaran of Anthropic Labs published Harness design for long-running application development, and buried in it is the single most useful sentence I've read on the subject:

Every component in a harness encodes an assumption about what the model can't do on its own.

Read that twice. Every retry wrapper, every decomposition step, every "let me re-read the file before editing" instruction is a written record of a model limitation you worked around. It's a changelog of weaknesses.

Which means your harness has an expiry date

Rajasekaran's follow-through is the part most people skip: those assumptions "can quickly go stale as models improve."

Anthropic's own example is concrete. Their team hit what they call context anxiety in Sonnet 4.5 — behavior that required building full context resets into the harness. When Opus 4.5 largely eliminated the problem, they removed the scaffolding. Not refactored. Removed.

I find this genuinely counterintuitive, because harnesses accrete. Nobody deletes a workaround. Every incident adds a guard, every guard adds latency and surface area, and none of it comes back out. Eighteen months later you're running an elaborate apparatus for defending against a model that no longer exists.

A harness you never revisit is a museum of your old model's weaknesses.

The architecture in that same essay is worth stealing regardless. Rajasekaran describes a GAN-inspired three-agent split — planner, generator, evaluator — built on the Claude Agent SDK, where a separate evaluator grades output against hard-threshold criteria. The justification is blunt and matches what anyone who has tried self-grading already suspects: agents skew positive when grading their own work. Separating generation from evaluation beats self-evaluation, structurally.

Hold onto that. It comes back in a minute.

A note on the other kind of harness

Two things share this word and conflating them will confuse you.

An agent harness makes the model do work. An evaluation harness measures whether it did. EleutherAI's lm-evaluation-harness is the reference implementation of the second kind — it's what powers the HuggingFace Open LLM Leaderboard, and it's been the gold standard for model benchmarking since well before "harness engineering" was a phrase. The tau-bench and tau2-bench runners are evaluation harnesses too.

Same word, opposite direction. One produces behavior, the other produces numbers about behavior. You need both, and you should be able to say which one you're talking about without a follow-up question.

The term also has research legs at this point, not just blog legs. By mid-2026 "harness engineering" shows up as a named section across a spread of arXiv work — SafeHarness, HARBOR, AutoHarness, HarnessFix, Externalization in LLM Agents. That's the usual signal that a practitioner term has crossed over.

Here's the part the essays list and then walk past

Go back through every harness taxonomy published this year. Observability appears in all of them. It gets one bullet, somewhere after sandboxing, and then the essay moves on to orchestration.

That ordering is backwards, and I'd argue it's the most consequential mistake in the current discourse.

Harness engineering is an empirical discipline. That's the whole premise — Trivedy's Terminal Bench result exists because someone changed a component and measured the delta. You alter a tool definition, a retry policy, a context-window strategy, and you need to know whether it helped. Not whether it felt better. Whether it helped.

Without per-call traces, per-agent rollups, and evaluation on real traffic, you aren't engineering a harness. You're guessing at one, with the confidence interval of a coin flip and none of the honesty.

import fluiq

fluiq.instrument(api_key="flq_...")

One line, and every LLM call, tool invocation, and agent-to-agent hop becomes a span you can compare across harness versions. That's not adjacent to harness engineering. Under Trivedy's own definition — everything that isn't the model — it is the harness.

And a harness constrains, it doesn't only orchestrate

The definition includes enforceable constraints. Most harness writing covers tools and context and stops politely before enforcement, which is a shame, because enforcement is where the interesting failures live.

Three primitives, all of them harness-level, none of them model-level:

PrimitiveWhat it doesWhy the model can't do it
Input gatesBlock a prompt before the model call, not after the damageA model asked to police its own input has already read the input
Output gatesScore the response before it reaches the caller or the next agentThe generating model is the least reliable judge of its own output
Tool allowlistsScope which tools an agent may call at allAn agent that can call anything has capability, not constraint

Notice that the middle row is Rajasekaran's separate-evaluator argument wearing different clothes. Generation and judgment want to be different components. That's true whether you're grading code quality or catching a credential on its way out the door.

import fluiq

fluiq.instrument(api_key="flq_...")
fluiq.eval(metrics=["hallucination", "relevance"])
fluiq.secure(mode="block", guardrail="strict")

Three calls. Observe every hop, evaluate on real traffic, enforce at the boundary. If the harness is everything that isn't the model, then tracing, evaluation, and security enforcement aren't tools you bolt onto an agent. They're constituents of it.

What I'd actually take from all this

The center of gravity moved. Prompt engineering was about the string you send. Context engineering was about what surrounds it. Harness engineering is about the entire executable environment the model operates inside — and the industry's two most model-rich organizations both published essays saying so, unprompted, six weeks apart.

Three things I'd hold onto:

Your harness encodes assumptions, and assumptions rot. Schedule the deletion, not just the addition. When a model upgrade lands, the question isn't only "what can we now do?" — it's "what scaffolding can we now remove?"

You cannot iterate on what you cannot see. Every published harness win is a measured delta. If you have no traces, you have no deltas, and every harness change is a vibe.

Constraints are harness components too. The gates and allowlists aren't a compliance checkbox sitting outside the architecture. They're the part of the harness that decides what happens when the model is wrong — which, on a long enough timeline, it is.

Stop tuning prompts. Start engineering the harness. And then, every few months, go delete part of it.
